# Schema comparison and proposed contract

`shared/terrain.schema.json` is a **heightmap rendering contract**, not a feature-record contract. It requires `id`, `name`, `body`, `width`, `height`, `cellSizeMeters`, `elevationsMeters`, and `source`. It permits `isSynthetic` and uses title-case `Earth|Mars|Moon`. It has no `schema_version`, `region_id`, `kind`, coordinates, scale/window, resolutions, resolution validation, DEM provenance/version, per-feature value/status/comparability/note, Earth filters, quality, processing version, or tags. Conversely v2.3 does not carry the heightmap dimensions, spacing, or elevation array. These schemas should remain distinct. The terrain example also uses a third naming convention (`elevations_m`, `sample_spacing_m`) that does not validate against the current terrain schema.

The current `data/processed` fixtures use `id`, `planet`, numeric `features`, and `isSynthetic`. `engine/adapters.py` maps `slope_deg` → `slope_median_deg` and `tri_m` → `tri_median_m`; infers `mock` status from `isSynthetic`, defaults legacy scale to `local` and legacy resolution validation to true, and defaults topographic comparability to resolution validation. These are **compatibility assumptions**, not measured validation. Every default is logged in `Dataset.defaults_applied` and `index.json`.

For v2.3, use a separate `shared/feature-region.schema.json` with the fields in the task. `data_status` must be `mock|observed|derived`; `quality.coverage` must be `full|partial|fallback_dem|none|pending`. In flattened Parquet use `<feature>`, `<feature>__status`, `<feature>__comparable`, and `earth_filters__<name>`. Set temperature comparable only when explicitly validated. Processing should supply `resolution_validated` and comparability per record and feature.
